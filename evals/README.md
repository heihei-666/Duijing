# 对镜 · 评测集

> 回答一个问题：**改了 prompt，怎么知道是变好了还是变坏了？**
>
> 在此之前这个项目答不上来。`tests/test_ai_layer.py` 测的全是管道
> （路由对不对、JSON 能不能抠出来），**没有一条在评估模型输出的质量**。

---

## 两层结构（为什么不在 CI 里跑 judge）

| 层 | 跑什么 | 花不花钱 | 在哪跑 | 证明什么 |
|---|---|---|---|---|
| **规则校验** `checks.py` | schema、观察上限、废话黑名单、长度、复盘块非空 | **免费**（`AI_PROVIDER=mock`） | **CI**（每次提交） | **管道没坏** |
| **LLM-as-judge** `judge.py` | 具体性 / 有无依据 / 可执行性 / 是不是废话 | 要真实 Key，几毛钱 | 本地或服务器**手动** | **观察准不准** |

**为什么 judge 不进 CI**：它花钱、要密钥、且模型输出本身有方差。
把这三样塞进 CI，得到的是一堆 flaky 红灯和一个公开仓库里的 API Key。
CI 该当的门禁是**确定性**的，judge 该当的是**质量报告**。

> ⚠️ **必须说清规则层的局限**：用 Mock 跑时，模型对每场辩论返回的是同样的几条罐头观察，
> 所以 12/12 通过**只说明管道是通的**，不说明观察是对的。
> 真正区分「模型有没有在读内容」的是 judge 层的 `repeated_observations` ——
> 12 场不同的辩论如果抽出同样几条观察，那就是在套模板，一眼能看出来。

## 用法

```bash
# 规则校验（免费、确定性）
python -m evals.run --mode rules

# 规则校验 + judge 打分（需要 Key）
python -m evals.run --mode judge

# judge 单独重跑 —— 读已有的规则层报告，不重新跑生成
python -m evals.judge --report evals/reports/rules-<时间戳>.json

# 只跑前 3 条，调试用
python -m evals.run --mode rules --limit 3
```

报告写到 `evals/reports/`（**不入库**，与 e2e 的产物同样处理）。

### 为什么 judge 要能单独重跑

这不是洁癖，是**被真实事故逼出来的**：

第一次在服务器上跑时，进程在规则层跑完、刚进入 judge 的那一刻**静默死掉**
（非 OOM，内核无记录、内存充裕、生产服务与数据完好，原因至今未定位到）。
而当时报告是在 judge 之后才写的 —— 于是 30 条规则层的结论**一起丢了**，
只能从头再跑一遍，白花一次钱。

改成了两件事：

1. **规则层报告先落盘**，再跑 judge。跑了几分钟的成果不该由一个后续步骤决定去留
2. **judge 独立成一条命令**，只需要 golden set + 已产出的观察，不重跑整个 App；
   而且**每判完一条就写一次中间文件**，再崩也不会全丢

用 `--mode judge` 时若 judge 中途失败，规则层报告已经保住了，
按上面第二条命令单独重跑 judge 即可。**生成那部分的钱不会白花第二次。**

### judge 用哪个模型

默认 **DeepSeek**，可用 `EVAL_JUDGE_PROVIDER` 改。

**为什么必须和被测模型不同**：被测的观察提取走 MiMo（方案 5.3 的路由），
裁判如果也用 MiMo，等于让同一个模型给自己打分，系统性偏袒无法被发现。

### judge 自己也有偏见

所以：分数**只做相对比较**（改 prompt 前后跑同一套），不当绝对真理；
报告里同时给出废话条数、错标条数、以及**跨用例重复的观察**——
最后一个不需要任何评分就能说明问题。

## golden set

`evals/golden/observations.jsonl`，一行一条：

```json
{"id": "arg-01", "layer": "论证结构", "topic": "...", "stance": "该",
 "user_turns": ["第一轮发言", "第二轮", "第三轮"],
 "forbid_substrings": ["你很棒"]}
```

- `layer` 必须是方案 3.1 的四层之一：论证结构 / 情绪与防御 / 互动策略 / 语言习惯
- `user_turns` **至少 3 轮**：两轮发言观察不出「互动策略」或「语言习惯」，那是编的
- 四层必须都有覆盖（`tests/test_evals.py` 会守）

### 当前是**合成数据**

没有用生产里的真实辩论记录。真实的更可信，但需要脱敏 + 人工标注。
合成数据的用途是**先把评测流程跑通、把基线量出来**；
面试时被问「样本从哪来」要如实说是合成的，不能含糊。

## 实测结果：prompt v1 → v2 → v2.1

同一套 golden set、同一个裁判（DeepSeek，被测走 MiMo，换源避免自评）：

| 指标 | v1 | v2 | **v2.1** | 总变化 |
|---|---|---|---|---|
| 具体性（5 分制） | 3.26 | 3.86 | **4.22** | **+0.96（+29%）** |
| 有依据（5 分制） | 3.51 | 3.88 | **4.42** | **+0.91（+26%）** |
| 可执行性（5 分制） | 2.40 | 2.92 | **3.27** | **+0.87（+36%）** |
| 判为废话 | 13 条 | 6 条 | **2 条** | **−85%** |
| 判为错标 | 16 条 | 7 条 | **5 条** | **−69%** |
| 完成打分 | 24/30 | 28/30 | 28/30 | +4 |
| 规则层通过率 | 100% | 96.7% | **100%** | 回归已修 |
| **跨用例重复的观察** | 3 类 | 2 类 | **0 类** | **套模板消失** |
| 成本 | 0.0691 元 | 0.0852 元 | 0.0895 元 | **+29.5%** |

prompt 长度：402 → 1297 → 1707 字符。**评分涨 26~36%，成本涨 29.5%** ——
这笔账划不划算取决于产品，但**至少它是可算的**，而不是靠感觉。

**最有力的证据不是分数，是这三条：**

1. v1 对几乎每条辩论都只回「回避追问」+「立场坚定」——它在套两个万能标签，
   根本没在读内容。v2 之后能识别出 golden set 里**设计好的**模式：
   循环论证 → 「循环论证未察觉」；以偏概全 → 「个案当定律」；
   绝对化措辞 → 「用绝对化措辞代替论证」。
2. **v2 起有 5 条用例主动不给优势**（v1 只有 1 条）。那几条本就是
   「只有弱点、没有对应优势」的设计 —— v1 会硬编一个「立场坚定」，
   v2 会说「没有依据」。**敢说没有，才是真的在读。**
3. v2.1 把**跨用例重复降到 0** —— 30 场不同的辩论，再没有两条抽出同样的观察。

### 三段迭代各自改了什么

| 版本 | 改了什么 | 为什么 |
|---|---|---|
| **v2** | 补四层定义；写清「什么不算观察」+ 一条自检；`reason` 必须原样引用用户原话 | 看基线数据定位：v1 通篇没提四层（16 条错标的主因）；只说「不要泛泛而谈」却没说**什么算**；优势侧零约束 |
| **v2.1** | 把「没依据给 null」**限定在两条观察上**，三个叙事块反过来必须写 | **v2 自己引入的回归**：规则层 100%→96.7%，arg-01 的 `next_time` 变空。严格性外溢到叙事块，模型连「下次怎么改」都不写了 |

### ⚠️ 这一节最该被看到的是 v2 的代价

**只看 judge 的三个分数，会得出「v2 全面变好」的结论 —— 那是错的。**

v2 的质量分确实全面上涨，但它同时让复盘卡片的「如果再来一次」那一栏变成空白。
**那个空块只有规则层能抓到。** 这正是两层设计存在的理由：
确定性检查和质量评分**互相看不见对方的盲区** ——
`next_time` 为空是硬伤，但它不表现为「分数下降」，
它表现为一个用户打开就皱眉的空白栏，而 judge 根本不看叙事块。

**v2.1 修好之后，规则层回到 100%，同时质量分继续上涨。**

### 仍未解决

judge 自己有 2/30 条返回了非法 JSON（arg-01、int-01，各版本都出现）。这是
**judge 层的健壮性问题**，与 prompt 无关：应该换成 `app/ai/structured.py` 那套
「schema 校验 + 失败重试一次」，而不是直接 `extract_json`。
**如实记在这里，不掩盖** —— 一个评测工具自己有 7% 的失败率，报数时就该说清楚。

## 评测集自己也会坏

**一个永远返回「通过」的评测，比没有评测更危险**——它让人以为有保障。

所以 `tests/test_evals.py` 守三件事：

1. golden set 每条都写对了（字段齐、层合法、发言够多、id 不重复）
2. golden set 有覆盖（四层都有，且不是同一条复制十遍）
3. **规则函数真的会失败** —— 每条规则都配了「故意违规必须被抓到」的反向用例

第 3 条最容易被忽略：如果 `check_observations` 因为一个拼写错误永远返回通过，
普通测试套件不会有任何反应。

## 怎么用它回答面试问题

> **「你改了 prompt，怎么知道效果变好了？」**

1. 跑 `--mode rules` 拿到硬错误基线（免费）
2. 跑 `--mode judge` 拿到质量基线：具体性 / 依据 / 可执行性 / 废话条数
3. 改 prompt
4. 两层各再跑一遍，对比报告
5. 报告里贴的是**两张表**，不是一句「感觉好多了」

这也是**失败样本回流**的入口：judge 判低分的那些用例，就是下一轮要改 prompt 的依据。
