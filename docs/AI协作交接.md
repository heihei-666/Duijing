# 对镜 · AI 协作交接说明

> 这份文件回答一个问题：**把这套东西交给下一个人（或下一个 AI 助手）时，怎么交代「上一个 AI 是怎么干活的」。**
>
> 项目本身的交接看 `docs/交接说明.md`；这份**只讲协作方式、操作习惯、以及踩过的坑**。

---

## 0. 先用一句话说清它的工作方式

> 上一个 AI 的流程是：**读代码和真实数据 → 改 → 跑单元测试 → 构建 → 直接部署到生产 → 在生产环境用无头浏览器验收 → 提交推送。**

它不会「改完让你自己测」。好处是交付的东西当场就是验证过的；
代价是**它会直接动生产环境**——这是交接时最需要对方知道的一点。

---

## 1. 它在哪里干活

它不只有仓库，还在这台手机容器里建了一整套工作目录。**这些目录不在仓库里，换个环境就没了**，所以下一位要么沿用，要么按 `e2e/README.md` 重建。

| 路径 | 用途 | 为什么在这儿 |
|---|---|---|
| `/sdcard/DSH/qingyu-diary` | 仓库本体（git 工作区） | 会话工作区 |
| `/root/djsw` | **前端构建目录**（复用 `node_modules`） | `/sdcard` 是 FUSE，`npm install` 极慢、`chmod` 无效 |
| `/root/djrun` | **后端测试目录**（复制 `app/ tests/ pytest.ini` 过去跑） | 避免污染仓库 |
| `/root/djvenv` | Python 虚拟环境（后端依赖） | —— |
| `/root/e2e` | 无头浏览器验收的历史现场（截图、结果 JSON） | 28MB，产物不入库 |
| `/root/djhooks` | **pre-commit 钩子转发器** | FUSE 存不住可执行位，见 §3.6 |

工具版本：Node v24.19.0 · git 2.43.0 · Python 3.12.3

**部署凭据**：SSH 私钥在容器内 root 的 `~/.ssh/` 下，服务器是阿里云 ECS（公网 IP 即 `duijing.xyz` 的解析结果）。
**私钥不在仓库里，也不会进仓库**——换人时请通过密码管理器单独交接。

> 🔑 服务器怎么连、怎么给新人开通访问、当前访问配置有哪些欠账：
> 见 [`服务器连接指南.md`](./服务器连接指南.md)。

## 2. 它的标准动作（可以直接照着复述）

### 发布一次前端改动

```bash
# ① 本地：同步源码到原生文件系统（跳过 FUSE）
rsync -a --delete --exclude node_modules --exclude dist \
  /sdcard/DSH/qingyu-diary/web/ /root/djsw/

# ② 类型检查 + 构建（build 脚本本身就带 tsc --noEmit）
cd /root/djsw && npx vite build

# ③ 产物权限：FUSE 的 umask 会让文件不可读，必须先放开
chmod -R a+rX /root/djsw/dist

# ④ 上传并原子替换
rsync -az --delete -e "ssh -i <私钥>" /root/djsw/dist/ <服务器>:/tmp/dj-dist/
ssh <服务器> "sudo rsync -a --delete /tmp/dj-dist/ /var/www/duijing/dist/ \
  && sudo chown -R www-data:www-data /var/www/duijing/dist && rm -rf /tmp/dj-dist"
```

### 后端改动

`git pull` → `systemctl restart duijing` → `curl -s 127.0.0.1:3000/api/health` 确认 `status=ok`。

### 跑测试

```bash
# 后端（160 项）
rsync -a --delete /sdcard/DSH/qingyu-diary/{tests,pytest.ini} /root/djrun/ && cd /root/djrun
/root/djvenv/bin/python -m pytest -q

# 端到端（会连生产站点，跑完必须清理账号，见 e2e/README.md）
DJ_INVITE=<邀请码> node e2e/accept.mjs
```

### 提交

```bash
git add -A -- <只加自己改过的路径>     # 绝不 git add -A 全量，避免带上半成品
git commit -m "..."                    # 钩子会自动扫描密钥
git push origin main
```

## 3. ⚠️ 它踩过的坑（**务必转达，这是这份文件最值的部分**）

### 3.1 它会在生产数据库里建真实账号

跑验收脚本时，它会注册真实账号、建真实辩论房，甚至**复刻一份你房间里的辩题和消息**来构造测试状态。

**必须转达的话**：*它跑完会清理，但你要检查它真的清理了。* 清理时只删测试账号、
**绝不碰 `user_id=1`**，并且要单独清孤儿行（SQLite 外键级联不总生效）。SQL 在 `e2e/README.md`。

### 3.2 它误判过「服务器国际网络不通」

排查部署问题时它一度认定服务器连不上境外，结论是错的——真实原因是一个代理 URL 写错
加一个解析器 bug。全局探测后 8/8 节点都是 HTTP 200。

**教训**：它下网络类结论时，会先做全局探测再定论；如果它只是口头说「网络不通」，要求它拿证据。

### 3.3 它把两条相隔 6 天的时间线混在了一起

在一次会话里，它读到「2 个房间」，后来又读到「7 个房间」，于是**怀疑数据库被人动过、
甚至怀疑自己误删了用户数据**，花了很长时间取证。真实情况是：那两条记录相差 6 天
（09-26 与 10-02），数据一直完好。

**教训**：它会因为上下文压缩而丢失时间感。**凡是它说「数据被改了 / 东西丢了」，
先让它 `git log --date=iso` 和 `stat` 对齐时间戳**，别急着相信结论。

### 3.4 它把 FUSE 的陈旧 mtime 当成了事实

它曾根据目录 mtime 断定「文件是 3 天前被删的」，但 `/sdcard` 是 FUSE，
**目录 mtime 根本不可信**（不随 unlink 更新）。当天构建明明成功了，文件不可能缺失。

**教训**：在这台机器上，**mtime 不能作为证据**，要用「能不能构建成功」这类行为来验证。

### 3.5 它会在取证上钻牛角尖

遇到想不通的现象（比如上面两条），它会连续十几轮命令深挖，占用大量时间。

**建议**：如果你觉得它在钻牛角尖，直接说「先记录现象，继续做正事」，它会照做。

### 3.6 它踩过的环境坑（会重复发生）

| 现象 | 原因 | 处理 |
|---|---|---|
| 提交时提示钩子「not set as executable」 | `/sdcard` 是 FUSE，`chmod +x` 无效 | 已配 `core.hooksPath=/root/djhooks` 转发器；**换机器要重建** |
| `npm install` 极慢 | FUSE | 在 `/root` 下构建 |
| 构建产物 403 | FUSE umask | `chmod -R a+rX dist` |
| workbox 降级 | 容器里 `os.cpus().length === 0` | 正常现象，不是 bug |
| `pip` 装不上 | 国内直连 pypi 要 12s | 用阿里云镜像 |
| git 报 dubious ownership | 容器环境 | `git config --global --add safe.directory '*'` |

### 3.7 它自作主张扩大过范围

它会顺手做你没要求的事，比如：修一个「从未生效过的密钥钩子」、
把散在仓库外的验收脚本参数化后收进仓库、给文档补验收记录。

**多数时候这是好事**（它会在提交信息和回复里说明），但如果你只要最小改动，
**明确说「只改 X，别动别的」**，它会严格遵守。

### 3.8 它不会自己发明规则

方案文档（`docs/新方案.txt`）没写的东西，它会**停下来问你**，而不是自己定。
例子：辩超计划轮数要不要设硬上限，它查完方案确认没写，就没有擅自加，
而是把两条路摆出来让你选。**这个习惯值得保留。**

## 4. 交给下一个 AI：第一段话可以这么说

直接复制粘贴即可（把尖括号内容换掉）：

```
这是一个已在生产运行的项目「对镜」，代码在 /sdcard/DSH/qingyu-diary（Gitee: main 分支）。

开始前必须先读这三份，不要跳过：
  1. docs/交接说明.md      —— 项目做了什么、没做什么、待决定事项
  2. docs/AI协作交接.md    —— 上一位 AI 的工作方式与踩过的坑（就是这份）
  3. docs/方案对照表.md    —— 方案要求 vs 实际实现的逐条核对

工作约定：
  · 与用户交流一律用中文
  · 改动前先读代码和真实数据，不要凭猜测
  · 构建在 /root/djsw 做（/sdcard 是 FUSE，慢且 chmod 无效），构建后 chmod -R a+rX dist
  · 提交只加自己改过的路径，不要 git add -A
  · 部署到生产前先跑测试；部署后在**生产环境**验证，不要只跑本地
  · 生产数据库里有真实用户数据：绝不删除或修改 user_id=1 的任何数据
  · 跑验收脚本会在生产库建测试账号，跑完必须清理，并单独清孤儿行
  · 方案文档没写的事，停下来问，不要自己定规则
  · 时间戳在这台机器上不可靠（FUSE），别用 mtime 下结论

当前已知的阻塞：域名 duijing.xyz 被阿里云按「未备案」拦截，外网打不开。
服务器本身正常（裸 IP 可访问）。详见 docs/交接说明.md §5。
```

## 5. 交给下一个人：先做这 5 项检查

1. **确认数据完好** —— 登录应用，看辩论列表、弱点墙、资产页是否与预期一致
2. **确认代码一致** —— `git fetch && git status`，本地与远端零差异、工作区干净
3. **确认服务活着** —— `systemctl status duijing nginx` + `curl 127.0.0.1:3000/api/health`
4. **确认备份可用** —— 从 `/var/backups/duijing/` 拿一份恢复到测试库，**这一步从没做过**
5. **确认承诺的事没落空** —— 对照 `docs/交接说明.md` §4，看哪些「没做」需要排期

---

## 6. 不要让 AI 单独做的事

- **轮换密钥**：`/opt/duijing/.env` 里的 AI Key 建议轮换，但请你自己操作
- **改生产数据库结构**：迁移前先备份，且不要让它「顺手清理」任何数据
- **改方案里没写的行为规则**：比如轮次上限、自动降级策略
- **决定域名怎么处理**：备案 / 换端口 / 换节点，这是你的决策，不是它的

## 7. 最后一句

它做得最好的一点是：**先验证再宣称**。每次交付都带生产环境的实测结果和截图，
做不到的会直说做不到。

它最需要被盯着的一点也是同一件事的两面：**它会直接动生产**。
给它明确的边界，它会守得很好；边界不清，它会按自己的判断往前走。
