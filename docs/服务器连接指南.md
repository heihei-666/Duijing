# 对镜 · 服务器连接指南

> 回答一个问题：**接手的人怎么连上服务器。**
> 顺带写清当前访问现状、怎么给新人开通、以及几个该整改的安全问题。

## 2. 三条能进去的路

### 路 A：阿里云控制台（兜底，永远不会丢）

**阿里云控制台 → ECS → 实例 → 远程连接 → Workbench（或 VNC）**

不需要密钥、不需要公网 22 通、不需要记得任何密码 —— 只要阿里云账号还在，就一定能进。
**这是最后一道保险，SSH 配置改坏了也救得回来。**

> 你最近一次就是这么进的：`last` 记录显示 10-02 22:49 和 22:52 两次登录来自
> `100.104.x.x`（阿里云内网地址，控制台 Workbench 的特征）。

### 路 B：SSH 密钥（日常推荐）

```bash
ssh -i <你的私钥> admin@duijing.xyz
```

当前 `authorized_keys` 里有 **3 把**公钥：

| 行 | 类型 | 指纹（后 8 位） | 备注 | 归属 |
|---|---|---|---|---|
| 1 | ECDSA nistp521 | `…ld9Jqc` | `swas-imported-key` | **你从阿里云控制台导入的** |
| 3 | ED25519 | `…qSBfU` | `duijing-deploy-temp` | **AI 部署时生成的（当前在用）** |
| 4 | ED25519 | `…MHNk` | `duijing-deploy-temp` | ⚠️ **残留，已无人使用** |

### 路 C：SSH 密码（当前开着，**不建议长期保留**）

```bash
ssh admin@duijing.xyz        # 直接输密码
```

服务器当前 `passwordauthentication yes`，而且 `permitrootlogin yes`（root 也设了密码）。
**这意味着公网可以直接对 root 试密码。** 详见 §5。

## 3. 给下一位开通访问（推荐做法：一人一把钥匙）

**不要把自己的私钥复制给别人。** 一人一把，谁走了就删谁的那一行，互不影响。

### 第 1 步：对方在自己电脑上生成密钥

```bash
ssh-keygen -t ed25519 -C "张三@duijing" -f ~/.ssh/duijing
# 提示设 passphrase 时，建议设一个
```

### 第 2 步：对方把**公钥**发给你

```bash
cat ~/.ssh/duijing.pub
```

公钥是可以随便公开的（`ssh-ed25519 AAAA… 张三@duijing` 那一整行）。
**私钥（没有 `.pub` 后缀的那个文件）永远不要发给任何人。**

### 第 3 步：你把公钥加到服务器

在服务器上（或从本机远程执行）：

```bash
# 对方公钥粘到 <PUBKEY> 位置
echo '<PUBKEY>' | sudo tee -a /home/admin/.ssh/authorized_keys
sudo chmod 600 /home/admin/.ssh/authorized_keys
sudo chown admin:admin /home/admin/.ssh/authorized_keys
```

如果对方现在只能用密码登录，也可以让他自己来：

```bash
ssh-copy-id -i ~/.ssh/duijing.pub admin@duijing.xyz
```

### 第 4 步：对方验证

```bash
ssh -i ~/.ssh/duijing admin@duijing.xyz
# 进去后确认身份与权限：
id && sudo -n true && echo "免密 sudo OK"
```

### 第 5 步：确认没问题后，再考虑收权

- 删掉不再使用的公钥行（比如 §2 表里的第 4 行残留）
- 删掉 AI 用的临时部署密钥（`…qSBfU` 那一行）—— `deploy/DEPLOY.md` §10.6 原本就是这么要求的
- 然后在**确认所有人都已配好密钥**的前提下，再关闭密码登录（见 §5）

## 4. 连上以后怎么确认连对了

```bash
# 服务活着吗
systemctl status duijing nginx --no-pager | head -20

# 后端健康（期望 status=ok、database=ok、ai.mode=hybrid）
curl -s 127.0.0.1:3000/api/health

# 网关健康
curl -sk -o /dev/null -w '%{http_code}\n' https://127.0.0.1/api/health -H 'Host: duijing.xyz'

# 数据在不在
sudo sqlite3 /opt/duijing/data/duijing.db \
  "SELECT 'users=' || (SELECT count(*) FROM user) || ' rooms=' || (SELECT count(*) FROM debate_room);"

# 看日志
journalctl -u duijing -f
sudo tail -f /var/log/nginx/access.log
```

## 5. ⚠️ 当前安全现状与整改建议

| # | 问题 | 风险 | 建议 |
|---|---|---|---|
| 1 | `permitrootlogin yes` + root 设了密码 + `passwordauthentication yes` | **公网可直接对 root 试密码**。Nginx 日志里已经有大量扫描器（zmap、zgrab、`/.git/config` 探测） | 配好所有密钥后：`PermitRootLogin prohibit-password`、`PasswordAuthentication no` |
| 2 | AI 生成的部署私钥**没有 passphrase** | 私钥文件泄露即等于服务器沦陷 | 交接后删掉这把，改用各人自己的带口令密钥 |
| 3 | `authorized_keys` 里有一把重复的 `duijing-deploy-temp` 残留 | 无人管理的历史密钥，不知道在谁手里 | 确认无人使用后删掉第 4 行 |
| 4 | 只开了 22/80/443，但 22 对全网开放 | 暴力破解与扫描 | 可选：安全组把 22 限制到你的常用 IP；或改用控制台 Workbench |

**整改顺序很重要**：先给所有人配好密钥并验证能登录，**最后**才关密码登录。
顺序反了会把自己锁在外面 —— 不过**阿里云控制台永远能救回来**（路 A）。

改 `sshd_config` 的标准动作：

```bash
sudo cp /etc/ssh/sshd_config /etc/ssh/sshd_config.bak
sudo nano /etc/ssh/sshd_config      # 改完先别关当前会话！
sudo sshd -t                        # 语法检查
sudo systemctl reload ssh
# 新开一个终端验证还能登录，确认无误后再关掉旧会话
```

## 6. SSH 完全进不去怎么办

按顺序试：

1. **阿里云控制台 → 远程连接 → VNC**（不依赖 SSH 服务本身）
2. 控制台 → 实例 → **重置实例密码**
3. 控制台 → 密钥对 → **重新绑定密钥对**（会覆盖 `authorized_keys`，注意先备份）
4. 控制台 → **发送命令 / 云助手**（不需要登录就能在实例上执行命令）
5. 以上都不行 → 控制台提交工单

**关键点：只要阿里云账号还在，服务器就丢不了。** 所以阿里云账号本身的
账号密码 + 绑定手机 + MFA，比任何 SSH 密钥都重要。

## 7. 一句话交接

> 日常用**自己的密钥** SSH 登录 `admin@duijing.xyz`；
> 进不去就用**阿里云控制台的 Workbench/VNC**，那是永远有效的后路；
> 换人时**给对方单独发一把公钥**，人走了删掉那一行，不要共用私钥。
