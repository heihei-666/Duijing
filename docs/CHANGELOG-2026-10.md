## 一、微信内置浏览器登录不了（线上故障）

### 症状

微信里登录成功，下一秒首页说未登录、被弹回登录页。普通浏览器完全正常。

### 诊断

nginx 日志给出了确凿证据（**同一秒内**）：

```text
22:46:20  POST /api/auth/login   → 200   ← 登录成功，服务端下发了 Set-Cookie
22:46:21  GET  /api/status-bar   → 401   ← 下一秒就认不出他了
```

服务端下发的 Cookie 本身没问题（实测确认）：

```text
dj_token=…; HttpOnly; Max-Age=604800; Path=/; SameSite=none; Secure
```

**流量也没被截断** —— 微信请求完整到达，HTML/JS/CSS 全 200。

### 两次尝试，第二次才修对

| 尝试 | 做法 | 结果 |
|---|---|---|
| 第一次 | `SameSite` 从 `lax` 改成可配并置 `none` | ❌ **没解决**，修复后三次尝试依然 `login 200 → status-bar 401` |
| 第二次 | 加 `Authorization: Bearer` 兜底（**纯前端，后端本来就支持**） | ✅ 真机验证通过 |

**结论：微信不是「不发」Cookie，是根本不存。** 改属性救不了「存不下」。

### 一个必须说清的代价

token 从 httpOnly 变成 JS 可读，多了一条 XSS 攻击面。接受的理由是
同源、无第三方脚本，而**微信用户现在完全用不了** —— 两害相权。
这段推理写进了 `web/src/api/token.ts` 顶部。

### 踩到的坑（值得单独记）

后端 `extract_token` 里 **Bearer 优先于 Cookie**，这是刻意的
（显式凭证必须赢，否则多账号场景会越权）。因此**绝不能留下陈旧 token** ——
它会盖住仍然有效的 Cookie，**把「能用」变成「不能用」**。
三处清理（登出 / bootstrap 失败 / 401）都是为这条约束服务的。

### 我犯过的一个错

中途我用「微信请求里带 cookie 的有 0 条」当证据 —— **那条统计是无效的**，
nginx 默认日志格式根本不记录 Cookie 字段。真实证据只有状态码序列。
**教训：拿一个查不到的东西当证据，比没有证据更危险。**

## 二、找回密码（原本完全缺失）

### 问题

这个项目**没有邮件、没有短信、用户表里也没有邮箱字段**。
用户忘了密码，完整流程是：

```text
用户找开发者 → 开发者在服务器上直接写库 → 把新密码贴在聊天窗口里
```

2026-10-09 给 xww 重置走的就是这条。**那不是功能，是运维事故的日常。**

### 三条接口，分工不是随意的

| 接口 | 谁能用 | 关键约束 |
|---|---|---|
| `PATCH /api/account/password` | 自己 | **必须验当前密码** |
| `GET /api/admin/users` | 管理员 | **绝不返回 `password_hash`** |
| `POST /api/admin/users/:id/reset-password` | 管理员 | 返回一次性临时密码 |

- **自己改 → 必须验当前密码**。只看「已登录」不够：一台忘记登出的设备
  被人拿到，就能直接改密码把账号锁死。
- **管理员重置 → 不验旧密码**，因为管理员**本来就看不到别人的密码**
  （库里只有 bcrypt 哈希），「重置」是唯一可行的语义。
  所以它必须在 `/api/admin/*` 下受 `require_admin` 保护。
- 允许管理员重置自己 —— 忘记密码时这是唯一的自助出路，且调用者已通过
  admin 鉴权，不额外增加风险。

### 两条硬要求

1. **用户列表绝不返回 `password_hash`**，字段**白名单显式列出**而不是
   `user.__dict__`，这样将来给 user 表加列也不会顺手泄漏。
   测试除了逐字段断言，还把整个响应序列化后**扫 `$2b$` 前缀**。
2. **临时密码不含易混字符**（`0O1lI`）—— 它大概率要靠人念或手输。

### 如实写在响应里的已知限制

改密码 / 重置**都不会让其他设备已签发的 JWT 立即失效**。
无状态 JWT + 没有 token 黑名单，旧 token 在 7 天内仍可用。
要做「改密码 = 其他设备登出」需要加 `password_changed_at` 列并比对 JWT 的 `iat`
—— **那是独立的一次改动，没有混进来**。

## 三、未备案域名：Cloudflare Tunnel

### 问题

域名未备案，服务器在大陆。实测确诊：

```text
HTTP  :80                                   ❌ ECONNRESET
HTTPS :443 + SNI=www.duijing.xyz            ❌ ECONNRESET
HTTPS :443 不带 SNI（直接连 IP）              ✅ 握手成功，证书 CN=duijing.xyz
```

**带 SNI 就断、不带就通** —— 基于 SNI 的定向阻断，不是服务器故障。

### 关键认知：代理 A 记录无效，必须用隧道

| | 方向 | 阿里云看到什么 |
|---|---|---|
| 代理 A 记录（❌） | Cloudflare **入站**连源站 443 | 带域名 SNI 的入站连接 → **拦** |
| **Tunnel**（✅） | 源站**出站**连 Cloudflare | 一条出境长连接，**没有入站 SNI** → **不拦** |

**把 DNS 改成 Cloudflare 代理并不能解决** —— 被拦的那一段还在。

### 沿途踩的坑（全部写进 `deploy/CLOUDFLARE-TUNNEL.md`）

1. **改 NS 的位置容易找错** —— 阿里云的「云解析 DNS 控制台」是改解析记录的，
   改 NS 要去「域名控制台 → DNS修改」。实测就卡在这一轮。
2. **QUIC 在国内链路上会被干扰** —— 首次接入日志出现
   `failed to dial to edge with quic: timeout`。切到 HTTP/2（TCP 443）后稳定。
3. **控制台的 `Hostname routes` 是私有网络路由**，不是 public hostname
   （表单连 Service 都没有，且提示需要 Cloudflare One Client）→ 改用 API 配置。
4. **`noTLSVerify` 为什么必需** —— 回源到 `localhost:443` 用的是 Let's Encrypt
   证书，Cloudflare 从隧道那头校验会失败。
5. **本地 `config.yml` 的 ingress 会被忽略** —— token 式隧道以云端为准
   （`source: "cloudflare"`）。
6. **API 配 ingress 不会自动建 CNAME，且原 A 记录必须先删** —— 否则流量继续
   直连源站、继续被拦。**这是最容易卡住的一步。**

### region 是实测结论：**指定不了**

| `--region` | 结果 |
|---|---|
| 不指定（默认） | 4 条连接，全部 **LAX** |
| `us` | 4 条连接，LAX + SJC |
| `eu` / `hk` / `apac` | **0 条连接**（连不上） |

`--region` 是**全局参数**（放在子命令后面报 `flag not defined`），
而且它**不是地理 PoP 选择器** —— 隧道边缘是 anycast + BGP 自动选路，
从阿里云出发被路由到美国西海岸。客户端指定不了。

**代价：一次请求约 900ms。** 这是应急方案，不是长期架构。

## 四、前端适配宽屏

### 症状

用户原话：「在浏览器打开这个系统，很明显感觉竖屏观看体验，很难受」。

### 根因是两件事叠加

1. `AppShell` 把内容**写死在 `max-w-2xl`（672px）**居中
2. `TabBar` 在桌面浏览器上**仍是一条底部标签栏** —— 鼠标要跨越整个屏幕才能点到

### 改法

| 屏宽 | 布局 |
|---|---|
| < 1024px | 底部 4 Tab + 居中限宽（**完全不变**） |
| ≥ 1024px | 左侧竖向导航 + 放开的内容宽度 |

**宽屏仍然限宽（`max-w-3xl`），不是铺满** —— 铺满 1920px 会让每行文字长到
150+ 字符，阅读时眼睛要来回扫。**这是有意的取舍，不是没做完。**

### 顺手消掉一个必然踩的坑

4 个 Tab 原本只在 `TabBar` 里定义。改成两处渲染后，各写一份的话
**加一个 Tab 时必然漏改一处** —— 而「手机上能看到、电脑上找不到」这种 bug
在开发时几乎不会被发现。抽成 `components/layout/tabs.ts` 共用。

### 弹层（Sheet）宽屏居中

全站 5 处在用。三个必须一起改的细节，漏一个都出问题：

| 细节 | 不做的后果 |
|---|---|
| 四角全圆 | 居中后还只圆上面两角 |
| **投影方向** | `shadow-sheet` 是**向上**投的，居中后方向反了 → 新增 `shadow-modal` |
| **限高可滚** `lg:max-h-[85vh]` | 内容长的弹层居中后**被截断且滚不动** |

## 五、设置页按角色分组

### 从「平铺 6 个模块」到「5 个分组」

```text
管理   ← 仅管理员，放最上面
账号   → 我的邀请码 / 修改密码
社交   → 好友
通知   → 通知设置
数据   → 导出数据 / 注销账号
登出   （独立，不属任何组）
```

顺带**拆开了「关于与数据」** —— 它把导出和注销挤在一节，但一个是
「拿走我的数据」、一个是「删掉我的数据」，**心理分量完全不同**。

### 「修改密码」从常驻表单改成「一行 + 弹层」

第一版做成了三个常驻输入框。**那是错的**，三条理由：

1. **形态不一致** —— 设置页从头到尾是「标签 → 说明 → 按钮」的行形态，
   常驻表单是唯一的例外
2. **信息密度** —— 占约 200px 纵向空间，而这功能**一年可能只用一次**
3. **密码框不该长期停在屏幕上** —— 停留越久，被旁边人扫到、被录屏带进去的
   机会越多。**这是一条安全论据，不只是审美。**

形成了一条可复用的规则：

> **有始有终的表单任务 → 弹层**（填完就走）
> **危险动作 / 需要读解释文案 → 内联**（需要停留、需要二次确认）

### 面向角色扩展：判定收敛到一个函数

新增 `web/src/lib/roles.ts`。`rolesOf(user)` 返回**角色数组**而不是布尔 ——
「一个人可能有多个身份」是常态（管理员同时也是普通用户），判布尔值的话
`is_admin` 和 `is_user` 会互相打架。

现在只有 user/admin，直接读 `is_admin` 也够用。**但角色一变多，
每一处 `is_admin` 都要找出来改，漏一处就是某个角色看到了不该看的入口。**

**可新增性**：加模块 = 加一行（`SettingsRow`）；加分组 = 加一处（`SettingsGroup`）；
加角色 = 改一个函数（`rolesOf`）。组里没有可见内容时整组不渲染，视觉上不留空位。

Gitee 的 `main` 还停在旧提交。**两个远端的 main 必须都推。**

## 九、访客模式：先体验后注册（阶段 1–3）

### 起点：一个违反常识的第一屏

在此之前，未登录用户打开 `duijing.xyz` **直接就是登录/注册表单**。
而在那个时刻，用户对这个产品一无所知 —— 不知道辩论房长什么样、
不知道「AI 全程观察但不说」是什么体验、更不知道自己为什么需要它。

**在用户还不知道这是什么东西之前，就要他先交出账号密码。**
市面上有一定规模的产品几乎没有这么做的。

审批制（邀请码）本身没错，错的是**把审批放在体验之前**。

### 设计：访客 = 临时用户，不是「可空的 user_id」

辩论、观察、复盘这些逻辑有 **56 处依赖 `user.id`**。
把 `user_id` 改成可空，就要在每一处加判空分支，**漏一处就是线上 500**，
而且这类错误只在访客路径上触发 —— 正常用户的测试永远发现不了。

所以访客是一条 `is_guest=True` 的**真实 user 记录**，现有业务逻辑一行都不用改。
它唯一的不同是：用户名是 `guest_xxx`、密码是随机串（认领前不可登录）。

**注册 = 认领（claim），不是新建账号。** 把当前访客的 id 补齐用户名/密码、
`is_guest` 置 false 就完事 —— **转化路径上没有数据搬迁，也就没有搬迁失败的可能**。

### 成本：三道闸，全在花钱之前

匿名 AI 接口挂在公网上，不做限制就是把钱包挂上去。三道上限：

| # | 限制 | 存储 | 防的是 |
|---|---|---|---|
| ① | 单访客 2 次/天 | 数据库 | 同一个人反复试 |
| ② | 单 IP 2 次/天 | **内存** | 清缓存换个访客身份 |
| ③ | 全站 100 次/天 | 数据库 | 换 IP |

**限额文案本身是转化点**：三道报错的结尾都是「注册后继续」。
测试里断言了这句话必须含「注册」—— 如果限额只是拦人、不给出路，那它就是 bug。

`POST /api/auth/guest` 也查一次全站预算：建账号不花钱，但**建了却用不了**
是最糟的体验（用户走完三步才撞墙，账单上多一个永不使用的临时账号）。
这只是提前失败，真正的硬上限仍在发起辩论那一道。

### 前端：两个入口，一次跳转

落地页两个按钮都进访客模式，但落点不同：

- 「免费试用 3 分钟微辩论」→ `/start`，**预设题点一下就开局（零输入）**
- 「记下一件让你不爽的事」→ `/start`，但先摆出描述框并聚焦

「3 分钟」不是随口写的：`decide_max_rounds` 对新手 profile + 短辩题 + 无回环
算出 **4 轮**，正好落在 3 分钟左右。预设题直接发 `{topic, stance}`，
后端跳过 AI 出题那一步 —— 少一次调用，也更快。

**一个绕不开的坑**：入口意图（先看题还是先写字）不能用 `?mode=scene` 传。
`enterGuestMode()` 一返回 `status` 就变 authenticated，`RootLayout` 会立刻
`<Navigate replace>` 到 `/start`，**那次重定向会把任何带查询参数的跳转覆盖掉**。
所以意图存在 auth store 里，跳转只有 `RootLayout` 一处 —— 没有两条跳转打架的可能。

**认领成功不立刻跳走**：`is_guest` 一变 false，守卫会马上放行并卸载弹窗，
用户根本看不到「已经保存好了」。所以弹窗开着时守卫继续渲染蒙层，
等他点「进入对镜」再放行。

### 边界：访客只能进辩论房

弱点墙 / 资产 / 设置 / 多人邀请对访客是关的。不是技术上进不去
（访客是真实用户，接口全通），而是产品上不该让他进：那些页面此刻全是空的，
一个刚来 3 分钟的人看到「还没有弱点」只会得出「这东西没什么用」。

用户手敲 URL 进来时会看到统一那句：**「这是你的私人空间，注册后即可解锁专属弱点和优势资产。」**
—— 不静默重定向，因为直接跳会让人以为链接坏了。

### 已知缺口（不掩饰）

| 缺口 | 说明 |
|---|---|
| IP 计数在内存里 | 进程重启清零。要持久化得加 `created_ip` 列，本轮没做。第 ①③ 道是数据库计数不受影响 |
| **7 天清理任务没做** | `GUEST_RETENTION_DAYS` **只是个配置项，没有任何任务读它**，未认领的访客账号会一直保留。所以界面上**故意不写**「N 天后清理」—— 承诺一件后端没做的事比不承诺更糟。真要实现，得先决定「删一个 user 时挂在它 id 上的辩论 / 观察 / 复盘怎么办」，那是删除逻辑不是清理逻辑 |
| 访客页面边界只有前端 | 后端没有拦访客调弱点接口。数据都是他自己的，无越权，但成本类接口（如果以后加）需要在后端补 |
| 微信内置浏览器 SSE | EventSource 只带 Cookie，不带 Bearer 兜底令牌。和登录用户是同一套限制，不是访客引入的 |

### 上线后发现并修掉的一个真洞：认领绕过了邀请制

**用户验收时的原话**：「访客用户登录就不需要邀请码了吗……通过微辩论保存辩论记录，
可无需邀请码进入系统。」

确实如此。`POST /auth/claim` 早期**完全没有校验邀请码**，于是：

- 任何拿到落地页链接的人，辩完一场 → 点保存 → 拿到正式账号；
- 而认领后的账号**没有每日 AI 上限**（限额只对访客生效）。

**邀请制事实上等于开放注册，而且给陌生人开了无限 AI 额度。** 这是个真漏洞，
不是「设计取舍」—— 我上一版把它写成「有意的产品决定」，那是错的。

修复（认领与注册走同一道门禁）：

| 改动 | 说明 |
|---|---|

## 十一、陪练化 + 首页锚点（真实用户反馈驱动）

### 反馈的原话

> 「AI 太强，把我变成了被审判者 —— 被 AI 一步一步带着走。」
> 「没有锚点，不知道每天来干嘛。」

这两句都不是「某个接口坏了」，而是**产品性格**的问题。
而在这个产品里，性格只有一个载体：**prompt 和首页的第一屏**。

### 死穴一：AI 太强，用户成了「被审判者」

**根因**：`FIXED_SYSTEM_PROMPT` 的头一句是「你是辩论对手」。
模型对「对手」的理解就是「把对方驳倒」——于是它一路追问、指出漏洞、
逼到用户无话可说。问题不在模型的强度，在**角色定义错了**：
用户不是来参加辩论赛的，他是来照镜子的。

**改法**（`app/ai/prompts.py`，prompt 版本 v3.0 人格 / 复盘 v2.2）：

| 改动 | 内容 |
|---|---|
| 身份 | 对手 → **陪练**。目标从「把他问住」改成「让他把话说出来」 |
| 语气 | 明令禁止法官口吻，并**逐字点名**：「你这里逻辑错了」「你刚才回避了问题」一句都不许出现 |
| 台阶 | 写死触发条件（说「不知道」/ 发言少于 15 字 / 连续重复 / 出现挫败），命中就停止逼问，只能三选一给路，给完**停下来等** |
| 复盘 | 新增「不评判对错，只描述模式」整段：禁止判定输赢、禁止打分、禁止人格标签、禁止结尾劝人努力；正反例写死（「抗压能力不足」是人格判决，不是观察） |

**没有改的是对抗性本身。** 这个产品的核心价值是「有摩擦才照得见」，
AI 如果变成一味附和的应声虫，盲区就永远照不出来 —— 那是另一种失败。
所以强度保留在**论点上**，去掉的是**压迫感**。

复盘版本升到 **v2.2** 并做成 v2.1 的**显式增量**（`startswith` 断言守着）：
v2.1 修好的「三个叙事块不许为空」不能在 v2.2 里静默丢失，
因为那个回归当时是靠规则层评测抓出来的。

### 战术暂停：「我卡住了，给我提示」

新接口 `POST /api/debates/{id}/hint`，返回一句**话头**（≤60 字）。

三个刻意的不变量：

1. **不落库**。写进辩论记录会让 AI 下一轮知道「他需要帮助」而变得小心翼翼，
   也会让复盘把一句提示当成用户说过的话来观察。
2. **不占一轮**。它是一次求助，不是一次发言。
3. **必须能兜底**。和复盘不同（复盘宁可报错也不给假观察，因为假观察会污染弱点库），
   台阶是消耗品 —— 给一句通用的，远好过让用户对着按钮看报错。

### 死穴二：没有锚点

| 改动 | 为什么 |
|---|---|
| **事件卡提到首页第一位** | 原来第一行动是「和 AI 辩一轮」（4–8 轮、每轮 300 字、还要组织论点），门槛高到只有状态最好的那 5 分钟才够得上。「记一笔」的门槛是一句话。**留存不是靠每天辩一场建立的，是靠「今天也来了一下」** |
| 文案改成问句 | 「今天有什么让你不爽的瞬间？」比「记录事件卡」好 —— 前者具体到不需要思考就能回答，后者是一个功能名 |
| **「过去的你」对比区** | 首页唯一一块跨时间的数据：首次 7 天 vs 最近 7 天的撑住率。两侧各至少 2 次触发才显示（1 次撑住算不出趋势，只是噪声） |
| 一句问候 | 首页从「业绩看板」改成「你来了」 |

**「过去的你」变差时的措辞是这块最关键的地方**：
不能写「你退步了」——那这个产品就又变回了它本来要逃离的那种东西。
所以只做三件事：把两个数字并排摆出来（事实）、方向只用中性词、变差时
明确说「这不代表你退步了」并给出真实原因（记录越多，撞上的场景越难）。

### 问候语为什么不是 AI 生成的

用户的原话是「给一句温暖的 AI 开场白」。这里**刻意没有照做**：

- 首页首屏是产品最重要的 300 毫秒，为一句问候同步调模型要多等 1–3 秒
- 走异步队列要多一张表 + 一个调度任务，只为了每天一句
- 更关键：模型看不到「昨天他有没有撑住、连续几天、写过几张卡」，
  它写出来的温暖只能是泛泛安慰 —— 那正是这个产品最不想要的空洞感

而规则恰好能说得**更准**：昨天撑住了就说撑住了，昨天破功就说破功。
所以这句问候是**产品自己的声音**，不假装是 AI 说的。

### judge 层结果：重复三次之后，第一版结论被推翻了两条

同一套 30 条 golden set、同一个裁判（DeepSeek 判，MiMo 生成）。
**v2.2 跑了 3 次**（每次 0.086–0.091 元，合计 0.264 元）：

| 指标 | v2.1（单次） | **v2.2（3 次均值 ± 标准差）** | 折算成 σ | 结论 |
|---|---|---|---|---|
| 具体性 | 4.22 | **4.08 ± 0.12**（3.96–4.19） | **1.24σ** | **不能判定**（噪声内） |
| 有依据 | 4.42 | **4.17 ± 0.13**（4.02–4.26） | **1.86σ** | 倾向下降，边缘 |
| 可执行性 | 3.27 | **3.10 ± 0.09**（3.02–3.19） | **2.01σ** | **下降可信** |
| 判为废话 | 2 条 | **1.0 条**（0/1/2） | — | 略好，但**不是清零** |
| 判为错标 | 5 条 | **6.3 条**（5/6/8） | — | 略差 |
| 完成打分 | 28/30 | **29.0/30** | — | +1 |
| 规则层 | 100% | **100%**（3/3） | — | 持平 |
| 跨用例重复 | 0 类 | **0 类**（3/3） | — | 持平 |
| 成本 | 0.0895 元 | **0.0881 元** | — | −1.5% |

**同一条 prompt、同一套用例，具体性在 3.96–4.19 之间波动（跨度 0.23）。**
而第一次跑完时我写的「下降了 3.3%」，差距只有 0.14 ——
**两次运行之间的差，和所谓「下降」是同一个量级。**

上一版报告的三条说法，更正如下：

| 上一版 | 更正后 |
|---|---|
| 「三分数各降 3–6%」 | 只有**可执行性**超过 2σ；具体性在噪声内；有依据边缘 |
| 「**废话清零**」 | **站不住**：0/1/2，均值 1.0 条 |
| 「成本降 4.4%」 | 用均值是 **−1.5%**（单次 0.0856 正好是三次最低） |

**共同错误只有一个：拿单次运行当结论。** 这是本轮最值得记下来的一条 ——
它和「v2 的回归只有规则层抓得到」是同一类教训的两个方向：
**前者说明单层检查会漏，后者说明单次采样会骗。**

保留项：**v2.1 只有单次运行**，它自己也可能偏高。严格做法要 v2.1 也跑 3 次，
但 `REVIEW_PROMPT_VERSION` 只能切复盘 prompt、切不动代码里的辩论人格。
所以只能说「可执行性的下降比另外两项更可信」，不能说「v2.2 确实变差了」。

### 顺手发现一个评测口径问题（这是决策点，不是能顺手改的 bug）

拆每条观察的 `actionability` 后发现：**优势观察系统性拿 2–3 分**。
原因不在生成质量，在裁判问错了对象 —— judge 的 rubric 是
「用户看完能改变什么具体行为」，但它把这个问题问了**观察标签**，
而产品设计里「下一步做什么」由复盘卡片的 `alternative_action` 承担。

所以 `actionability` 从 v1 起就是最低项（2.40 → 3.27 → 3.10），
**其中多少是质量、多少是口径，目前分不开。** 三个选项
（改问复盘卡整体 / 只对 weakness 打分 / 承认结构性低分）写在 `evals/README.md`，
**当前先不动评测口径** —— 换尺子会让「v2.2 变差了多少」这个问题失去参照。

详细分析写在 `evals/README.md`。原始报告（不入库）在服务器
`/opt/duijing/evals/reports/judge-20261018-*.json`（三次各一份）。
